## Responsibility

Repository-wide development orchestration and conformance gates that do not belong to one product package. These scripts validate architecture, specification, and artifact assumptions; they never implement product behavior.

## Boundary

- **Owns:** the multi-process development launcher; exact-version/catalog validation; the PI binary-seam canary (core `pi` packages and the plugin host surface alike); module dependency/import boundary validation, subpath- and types-only-granular; a post-build scan of the shipped web bundle for what must never reach it; and a committed, diffable dump of `plugin-api`'s and `plugin-ui`'s effective TypeScript surface; declared-spec-surface to TypeScript-barrel conformance, one or several barrels per spec.
- **Public surface:** the root `package.json` commands consumed by developers, Husky, and CI: `check:deps`, `check:boundaries`, `check:seams`, `check:spec-surface`, `check:web-bundle`, `api:update`, `api:check`.
- **Allowed deps:** Bun/Node, the TypeScript 7 `typescript/unstable/*` API (the async `tsgo` client plus AST type guards), `pi-spec-graph/core` for the canonical spec/frontmatter model, and `mdast-util-from-markdown` for CommonMark block structure; read-only inspection of workspace manifests and source trees; the public package metadata and bundle outputs each check validates. `scripts/api-report.ts` is the one exception that shells out to the pinned `tsc` binary (`Bun.spawn(["bunx", "tsc", …])`) rather than driving `typescript/unstable/async` directly, since declaration emission is a `tsc` CLI feature the async client does not expose.
- **Forbidden:** product runtime logic, a second source of package or feature behavior, editing source as part of a check, or importing application internals to execute them.

`check:boundaries` runs the checker's focused tests before scanning the real workspace. It enforces both manifest edges and static source imports, including type-only, dynamic, re-export, CommonJS, import-type, package-subpath, and relative cross-module forms. Generated/build directories, including Hutch's projected `.hutch` SDK trees and transient `.cottontail-tmp` loaders, are excluded. The current product rings and launcher edges are exhaustive: contracts and `pi-delegation` → none; `pi-subagents` → `pi-delegation`; shared → contracts; server → contracts/shared plus its bundled extension, delegation, and plugin packages; web → contracts, plugin-api, plugin-ui, and each plugin package; CLI/desktop → server/shared plus each plugin's `./build-support`; artifact-tests → CLI/server/shared. Product packages may not import artifact-tests. A future composition root must add an explicit rule rather than silently inheriting access to every workspace package.

An `allowed` entry may be a bare package name (the whole package, any subpath, value or type position) or `{ target, subpath?, typesOnly?, from? }`: `subpath` narrows the edge to one declared `package.json#exports` key (e.g. `./contracts`), `typesOnly` additionally requires the importing statement itself to be type-only (an `import type`/`export type` clause, a per-specifier `import { type X }`/`export { type X }` whose named bindings are all type-only, or a type-position `import("…")`) — a value import of the same subpath still violates — and `from` restricts the entry to files under `<root>/<from>`, so two entries for the same target/subpath can grant a value edge from one subtree of the importing package and a types-only edge from another. This is what lets a builtin plugin package's own `./host`/`./manifest`/`./contracts`/`./build-support` subpaths reach `packages/server`, and `./manifest`/`./web` reach `apps/web` as values while `./contracts` reaches it as types only, without opening the rest of the package (its `./host`, in particular, must never be reachable from the browser bundle — `check:web-bundle` is the backstop that checks the shipped artifact rather than the source graph). It is also what lets `plugin-blueprint`'s `host/` call `ctx.dependency(specDialectContract)` — a genuine value use of `plugin-spec-dialect`'s `./contracts` subpath, per plugin-api SPEC.md's "Calls" grant — while `plugin-blueprint`'s `web/` may only reach that same subpath as types. A rule may also declare `internal: [{ from, forbid }]` entries: a same-package relative (or self-referencing) import from a file under `from` that resolves under any listed `forbid` directory is a violation even though the package-level edge is always allowed — this is how a plugin's `web/` is kept out of its own `host/`. Every declared subpath is itself checked against the target's real `package.json#exports` keys, so a typo'd or stale entry in `MODULE_RULES` fails the gate rather than silently admitting nothing.

`check:seams` also runs a second, unrelated loop over this repo's own plugin host surface — `packages/plugin-api/src/**`, every `packages/plugin-*/host/**`, and `packages/server/src/plugins/**` — for the same class of bundler-opaque dynamic `import(...)` it hunts for in pi's `dist/*.js`. Its allowlist holds exactly one entry, `packages/server/src/plugins/external.ts`'s `importExternalHost`, which loads an external plugin's host module from an absolute, content-hashed `file://` URL known only at runtime (plugin-adoption.md S11); a new opaque import anywhere else in that surface fails the gate the same way an unregistered pi import does.

`check:web-bundle` (`scripts/check-web-bundle.ts`, run after `bun run build:web`, CI-only) scans the built `apps/web/dist/assets/*.js` for what must never reach the browser: `node:fs`, `@anthropic-ai/sdk`, `openai`, a typebox schema-value marker, and any plugin `./host` module id. The typebox marker is the pinned version's actual runtime tell rather than an assumed one — `typebox` 1.x's `IsKind` (`type/types/schema.mjs`) checks a plain `"~kind"` string property, not the `Symbol.for("TypeBox.Kind")` of older typebox majors, so a schema built as a *value* (`Type.Object(...)` evaluated at module load, not erased as a type) leaves that literal string in the minified output; re-verify against `node_modules/typebox` on a typebox bump. The `./host` check is two signals rather than one: a chunk file named `host-*` (Vite already names a plugin's lazily-split `web/index.ts` chunk `web-*` and its `manifest.ts` chunk `manifest-*`, so a same-shaped `host-*` chunk would mean a host half got bundled for the browser) and a literal `@thinkrail/plugin-<id>/host` substring in any chunk's text. This is a backstop over the artifact, not a replacement for `check:boundaries`' source-level `internal` rule — the two catch the same mistake at different points, and only the bundle scan can catch a leak that arrives through a path the import-graph checker cannot see (a typebox value transitively pulled in through an otherwise-legitimate `./contracts` edge, say).

The committed API report (`scripts/api-report.ts`; root scripts `api:update` and `api:check`) is `plugin-api`'s and `plugin-ui`'s `.api` file, the Kotlin-project-style checked-in surface dump plugin-adoption.md's `module-plugin-api` spec calls for. For each entry (`plugin-api`'s `index`/`host`/`web`, `plugin-ui`'s `index`/`markdown`/`editor`/`visualization`) it runs `tsc -p <pkg>/tsconfig.api.json --outDir <tmp>` — TypeScript 7's `tsc` supports `--declaration --emitDeclarationOnly` cleanly, so the `typeToString`/`api-extractor` fallbacks the parent spec allows were not needed — then walks the entry's emitted `.d.ts` and every sibling `.d.ts` it relatively imports (external package types are left as `import`/`import type` lines, never inlined), concatenating them in that order (entry first, the rest sorted by path) into `<pkg>/api/<entry>.d.ts.api`. `api:check` regenerates into a temp directory and diffs; `api:update` overwrites the committed copy. Each package's `tsconfig.api.json` extends its own typecheck config (`plugin-api`'s extends the wider `tsconfig.web.json` and restates the three entry files as `include`, since the split host/no-DOM and web/DOM tsconfigs each cover only part of the package) with declaration emission turned on and a `./dist` default `outDir` (already `.gitignore`d) for the rare direct, unwrapped `tsc -p` invocation; the script itself always overrides `--outDir` to a throwaway temp directory. Runs in CI, alongside `check:spec-surface`, never in the pre-commit hook.

`check:spec-surface` enrolls only valid specs tagged `public-surface-checked`. Enrollment is explicit so adding prose cannot silently turn enforcement off: an enrolled spec must retain a bare backticked identifier list and a discoverable TypeScript barrel, or the check fails. Unenrolled prose surfaces remain descriptive and are reported only by `--list-skipped`.

A spec whose package has more than one entry point pins them with a `surfaces:` frontmatter list (paths relative to the spec, e.g. `[src/index.ts, src/host/index.ts, src/web/index.ts]`) instead of the single barrel `check:spec-surface` otherwise infers next to the spec file. It then expects exactly that many "Public surface"-labelled blocks in the document, matched to the list **by the parenthetical subpath in each block's own label** (`` - **Public surface (`./host`):** ``) rather than by document order — a block with no parenthetical (a heading-only surface) is treated as `.`. A mismatched count, a block's subpath naming no `surfaces:` entry, a `surfaces:` entry with no matching block, an unresolvable path, or a block that is not a bare identifier list is a violation. `packages/plugin-api/SPEC.md` and `packages/plugin-ui/SPEC.md` are enrolled this way.

The TypeScript compiler resolves the barrel's effective export names, including type-only and default exports and transitive re-exports; a CommonJS `export =` assignment is the module's singular `default` surface rather than the assigned value's synthetic members. An unresolved re-export is a violation rather than a silently incomplete surface. The declared and effective name sets must match in both directions. Filesystem-level tests exercise enrollment, resolution, and failure behavior through the same runner CI invokes.

## TypeScript access (decision, 2026-09)

TypeScript 7 ships the native `tsgo` compiler and no JavaScript parser or checker: the `typescript` package
exposes only `tsc` and the `unstable/*` API. The three checks that read TypeScript syntax or symbols
(`check:seams`, `check:boundaries`, `check:spec-surface`) therefore drive the bundled `tsgo` server through
`typescript/unstable/async` via `scripts/tsProjects.ts`. Each run declares an in-memory `tsconfig` (real files,
virtual config) so that arbitrary file lists — pi's `dist/*.js`, every workspace source tree, a barrel outside
its package's `include` — become a project without touching disk; the syntax-only checks open a lib-free,
resolution-free project, and the spec-surface check `extends` the barrel's nearest `tsconfig.json` (or a
Bundler-resolution fallback) with the barrel appended to its files. The synchronous `unstable/sync` client is
unusable under Bun (it reads Node's private stream handles), so the checks are async end to end. The
`unstable` prefix is an accepted risk: the exact catalog pin makes any API drift a reviewable bump.
